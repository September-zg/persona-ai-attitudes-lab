# AI 辅助开发记录

## 1. 使用的工具和责任边界

本项目使用 OpenAI Codex 作为 Agentic AI 编程工具。AI 协助完成需求拆分、代码草拟、界面文案、测试设计、错误排查和部署排查；项目负责人负责决定测量范围、检查代码、运行测试、核对公网行为，并对最终提交负责。

项目定位为教育/研究探索原型，不是临床、医学、招聘或诊断工具。计分规则固定在版本化的 `scoring.py` 中，运行时不让模型决定分数。

## 2. 问题拆分和系统设计

我把任务拆成五个可验证部分：

1. 测量设计：五大人格 20 题、AI 态度 6 题、1–5 分量尺和反向题键。
2. 参与者流程：说明与同意、人格部分、AI 态度部分、必答检查、结果和可选反馈。
3. 数据流程：服务器 JSON 保存、浏览器本地回退、服务端重算、研究者汇总。
4. 统计展示：逐题分布、维度均值、Cronbach α、Pearson 相关和反馈摘要。
5. 验证与部署：边界值、非法输入、导航、重复提交、权限、HTTPS 同源请求和 Render 部署。

技术方案保持简单：原生 HTML/CSS/JavaScript 前端、标准库 Python HTTP 服务器、JSON 文件存储。这样可以在没有构建工具和第三方依赖的情况下运行，也便于逐行检查生成的代码。

## 3. 代表性 AI 交互、输出和人工判断

### 交互一：把开放要求拆成最小可用流程

我要求 AI 先列出参与者流程、数据结构和研究者汇总需求，再写代码。AI 生成了首页、两部分问卷、结果页和仪表盘的初版。人工检查后保留了“同意后开始、两步问卷、提交后反馈”的主流程，并删掉了没有必要的个人信息字段。

### 交互二：固定计分规则并验证反向题

我要求 AI 把计分从页面脚本中抽成 `scoring.py`，明确使用 `6 - 原始回答`，并为正向题、反向题、缺失值、非整数和超出 1–5 的回答写测试。后来又发现服务端如果信任浏览器传来的 `scores`，参与者可以篡改结果，因此改为服务端完全根据 `answers` 重算并覆盖分数。

### 交互三：修正小样本统计误读

AI 初版可能在样本不足时显示 α 和相关。我要求增加至少 10 条完整提交的门槛，并在页面中说明 α 和 Pearson 相关只能作探索性描述，不能证明信度、效度或因果关系。

### 交互四：修正反向题导致的 α 计算错误

早期汇总把原始回答和反向回答混在一起计算，造成负 α。通过逐题检查发现问题来自 α 计算前没有统一题目方向。修复后，α 的输入先按题目键进行反向转换；同时保留负 α 提示，避免把异常结果当成结论。

### 交互五：修正公网 HTTPS 下的接口和权限问题

公网页面曾经使用错误的 API 地址，且研究者页面可能在未认证时直接请求汇总。通过 Render 日志和浏览器检查定位后：

- 前端 API 改为同源 `/api`；
- 脚本增加缓存版本号；
- `?view=admin` 先显示研究者登录页；
- `/api/summary` 和导出请求发送 `X-Admin-Token`；
- 未带令牌的汇总请求返回 401。

这仍是共享令牌保护，不是完整账户系统；这个限制已写入报告。

## 4. 验证 AI 输出的方法

验证分为三层：

- **静态检查**：Python 编译检查、计分配置中 26 个题目 ID 的唯一性和完整性。
- **单元/API 检查**：正向和反向计分、边界值、非法类型、缺失题目、输入不可变性、服务端重算、令牌拒绝与接受。
- **浏览器/部署检查**：同意门槛、分步导航、必答校验、结果页、反馈提交、移动端布局、公网首页、研究者登录和 Render Live 状态。

当前可复现的命令是：

```bash
python3 -m py_compile server.py scoring.py scoring_examples.py seed_synthetic.py
python3 -m unittest discover -s tests
python3 scoring_examples.py
```

- 测试套件目前有 18 项测试，运行结果为全部通过。

- 合成验证数据明确标记 `syntheticTest: true`，只用于检查计分和分析，不能计入真实试点。

## 6. 尚未完成的工作

AI 和本地测试不能替代真实用户评估。至少 10 名独立参与者、匿名反馈、完成率和改进建议必须由项目负责人实际收集后填写，不能由 AI 生成。当前项目仍使用本地 JSON 和共享令牌，尚未达到正式数据库、账户系统或访问审计的生产级水平。
