# E. 简短技术报告

> **版本与证据范围（2026-09-13）**：当前恢复版入口只加载 `app.js`，题目、计分和页面渲染均包含在该文件中；`questionnaire.js`、`analysis.js` 是仓库中保留的模块化开发代码，不能将其测试通过等同于当前线上 UI 全部通过。历史版的返回修改、五项反馈、用时统计、保存失败阻止跳转和后台维度分数分布不应宣称为恢复版已实现。恢复版包含均值和逐题分布；均值不等于维度分数分布，此项任务要求仍需补齐或明确列为不足。下文涉及“新版”的功能和测试记录应按历史开发记录阅读。


## 1. 我构建了什么？

本报告的正式试点统计使用 11 位独立参与者和 7 条反馈；部署后的额外测试记录不纳入试点分析。

**Personality & AI Attitudes Lab** 是一个教育/研究探索网页平台。参与者阅读说明并同意、完成 26 题、看到图形与分数解释，然后可提供反馈；研究者通过密码查看多人汇总及导出备份。

[测评网站](https://persona-ai-attitudes-lab.onrender.com/) · [研究者入口](https://persona-ai-attitudes-lab.onrender.com/index.html?view=admin) · [源码仓库](https://github.com/September-zg/personality-ai-attitudes-lab)

两种入口位于同一公网服务，不要求分别部署两个网站。本地复现步骤见 [README](../README.md)。

## 2. 测量哪些构念？

五大人格共 20 题：外向性、宜人性、尽责性、神经质、开放性各 4 题。采用 Mini-IPIP 形式与计分方向，中文是项目翻译；其中开放性对应智性/想象相关题意，不是能力测试。

AI 态度共 6 题：感知效益与使用意愿（U1/U2）、信任（T1/T2）、风险顾虑（R1/R2）各 2 题。题目自编且覆盖有限。此前“感知效益”和“信任与采纳”的名称不完全对应内容，现已纠正说明；原题、维度键和计分未变。

## 3. 为什么选择它们？

五大人格提供已有的描述框架；AI 态度与当前学习和工具使用场景相关。研究问题是：在小规模试点中，人格维度分数与 AI 态度维度分数是否一起变化？选择三个 AI 侧面，是为了同时呈现效益/使用意愿、信任和顾虑；不能将它们加成无定义的“AI 总分”。

## 4. 如何计分？

使用 1–5 分。人格题问符合程度，AI 题问同意程度。反向分为 `6 - 原始回答`；每个维度为统一方向后题目均值。不对缺失题补 0，不提前舍入，不显示常模百分位。

`scoring.py` 固定规则，服务端忽略浏览器分数并从原答案重算。`questionnaire.js` 和 `analysis.js` 提供前端离线计分与研究者分析，跨语言测试核对键和结果。具体键表与来源见 [measurement-spec.md](measurement-spec.md)。

## 5. 使用什么技术？

原生 HTML/CSS/JavaScript、SVG、Python 标准库 HTTP 服务器、JSON 文件、GitHub、Render。保持运行依赖少，便于老师下载复现；Node.js 仅用于开发测试及生成汇总证据。

服务端保存匿名编号、答案、计算分数、提交时间、新版完成用时和可选反馈，不写入姓名或邮箱；静态资源白名单不暴露运行数据，汇总及恢复接口校验 `ADMIN_TOKEN`。JSON 使用写锁和原子替换。该架构仍不是生产级数据库或账户体系。

## 6. 如何使用 Agentic AI？

使用 Codex 拆解要求、写代码和测试、解释计分、排查浏览器与部署、整理反馈。负责人不断通过真实截图和手机体验指出问题，并负责真实招募与最终判断。代表性交互及修正见 [AI_DEVELOPMENT_RECORD.md](AI_DEVELOPMENT_RECORD.md)。运行时没有 LLM 计分或心理解释请求。

## 7. 从试点参与者学到了什么？

导出证据包含 11 份完整回答、7 条反馈，项目负责人确认向不同朋友发放且为 11 位独立参与者。整体操作评分均值 4.14/5（n=7）；反馈认可简洁界面，也提出题目应更具体、图表应更直观。最关键的意见是不理解结果含义及人格与 AI 态度的联系。

因此新版增加人格图与展开解释，说明研究问题，同时明确结果不等于职业建议。增加五项体验反馈以便复测。旧记录缺少用时和开始人数，不计算完成率，不声称新版已经由原 11 人验证。完整分析与证据见 [PILOT_EVALUATION.md](PILOT_EVALUATION.md)。

## 8. 遇到什么问题？

本地文件、GitHub 提交与 Render 部署曾不同步；API 失败后显示结果或回退本机数据会混淆保存状态；旧后台缺少维度分数分布；README 对没有终端经验的人不够清楚。还有共享令牌、本地 JSON 持久性和原生浏览器输入中文等限制。

试点分析也显示尽责性 α=-0.80。核对反向键后仍为负，因此结果保留并标注需复核，不将它伪装成量表通过验证。

## 9. AI 犯过什么错误？

本次可检查的错误包括：把离线预览写进说明却始终请求服务器；保存失败仍进入结果；汇总读取失败时不区分本机回退；用维度均值条替代要求中的分数分布；仅保护汇总接口却仍提供整个静态目录；文档对负 α 原因作了过强断言。

参考建议中“AI 曾写成 5-score”只是示例，本项目没有证据证明发生过，不写成真实经历。具体修正依据见开发记录。

## 10. 如何验证并修正？

通过 Python 计分与 HTTP 测试、JavaScript 与 Python 一致性测试、浏览器完整流程及窄屏检查。真实答题从授权接口导出后重算，生成不含逐人原始数据的汇总证据；更新前备份，恢复采用仅追加、可重复执行的合并。

```bash
python3 -m unittest discover -s tests
python3 scoring_examples.py
node --test tests/test_analysis.cjs
```

逐项结果、截图与发布状态见 [verification.md](verification.md)。自动化验证只能说明对应案例通过，不能证明量表效度或所有设备都无问题。

## 11. 再有一周会改进什么？

1. 优先接入持久数据库与自动备份，明确保存期限、联系和删除流程。
2. 让反馈中表示困惑的参与者复测新版，记录理解、用时与失败事件。
3. 审查中文翻译和 AI 题组内容，再以新问卷版本扩大题数；不同版本不直接混合。
4. 使用个人账户与角色权限代替共享研究者密码。
5. 扩展便利样本以外的招募与无障碍测试，区分可用性、信度和效度证据。

该项目展示“构建—验证—试点—改进”的过程，仍是有明确局限的教育原型。
